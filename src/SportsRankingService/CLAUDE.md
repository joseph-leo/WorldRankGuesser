# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A .NET 11 run-once console app, imported into the WorldRankGuesser repo on 2026-09-21 (`src/SportsRankingService`), that scrapes world sports rankings (FIFA, ICC, World Rugby, BWF, etc.) from public web pages and JSON APIs, normalizes each feed to a `RankingSnapshot` (sport / event / gender / ranking date / one entry per ranked athlete, pair partner or team: position, ISO3, competitor, points), and stores it in SQL Server (`WorldRankGuesser`) as an immutable release only when the feed's content or federation date changed. `tools/WebScrapingBenchmarks` holds BenchmarkDotNet benchmarks (outside the solution) and `tests/SportsRankingService.Tests` holds xUnit tests.

## Commands

All commands run from the repo root unless noted.

```powershell
docker compose up -d --wait                              # local SQL Server 2022 (sa / Rankings_Dev1!, port 1433, loopback-only); the repo root's compose file
dotnet tool restore                                      # repo-local dotnet-ef (the version in .config/dotnet-tools.json at the repo root)
dotnet ef database update --project src/SportsRankingService   # apply the dbo migrations (the app never migrates itself); on a new database, before the game's
dotnet build WorldRankGuesser.slnx                       # the whole solution, this project included
dotnet run --project src/SportsRankingService            # fetch every enabled feed once, save, exit (0 = all saved, 1 = a feed failed)
dotnet run --project src/SportsRankingService -- --only "Cricket Women" --only Soccer   # only the feeds whose "Sport Event Gender" name contains a pattern's words in order
dotnet run --project tools/WebScrapingBenchmarks --configuration Release   # run benchmarks
dotnet test tests/SportsRankingService.Tests             # parser, resolver, fetcher, snapshot and repository tests; no external network (the curl tests use loopback and need curl on the PATH), SQLite in-memory for the repository
dotnet ef migrations add <Name> --project src/SportsRankingService --output-dir Persistence/Migrations   # after changing the entities
```

**Tests are sample-based.** `tests/SportsRankingService.Tests/Samples/` holds one synthetic response per feed, written by `Samples/generate.mjs` in exactly the shape its parser reads (`SAMPLES.md` lists the shapes); nothing in the repository is copied from a federation's site. Parser tests are pure: `new XParser().Parse(Sample.Read("..."))`, then assert count and known positions. `Feeds.All` is the one list of every feed shape; `SampleCountryCodesTests` runs it over the samples and `CaptureTests` over real responses saved under the git-ignored `Captures/` folder (same file names; skipped when the folder is absent), which is how a live format change is caught before a run. `RankingSourceRunnerTests` covers the whole pipeline for one item with a fake `IHttpFetcher` keyed by URL, including resolver round-trips. A skipped test in `MissingSourcesTests` names a feed whose source is dead or blocks scripted clients. Never make a test pass by weakening its assertions. `InternalsVisibleTo` exposes internals to the test and benchmark projects.

`appsettings.json` and `serviceconfig.json` are copied next to the binaries and the host's content root is `AppContext.BaseDirectory`, so the process runs from any working directory. There is no timer: the process runs every enabled feed once and exits; schedule it weekly with Task Scheduler or cron (README).

The project inherits `net11.0` from the repo root's `Directory.Build.props`, and the SDK from its `global.json`; EF Core is the same 11.0 build as the game's, and `dotnet-ef` comes from the root tool manifest. `dotnet ef` runs `Program` at design time with `--applicationName` to find the host; `Program.cs` skips the command line when `EF.IsDesignTime` is set, so that argument is not a usage error.

Which benchmark runs is hardcoded in `tools/WebScrapingBenchmarks/Program.cs` (`BenchmarkRunner.Run<ScrapeServiceBenchmark>()`); swap the type to run `CountryUtilBenchmark`. `ScrapeServiceBenchmark` builds the real pipeline from `serviceconfig.json` and hits every enabled live URL, no database.

## Persistence

Code-first EF Core in `Persistence/`; migrations live in `Persistence/Migrations/`. Two tables: `RankingReleases` (one immutable row per published ranking table per feed: sport, event, gender, `RankingDate`, `IsFederationDate`, SHA-256 `ContentHash`, `FirstSeenAt`, `LastSeenAt`) and `RankingRows` (`ReleaseId`, `Ordinal`, `Position`, `ISO3` varchar(3), `TeamName`, `Competitor`, `Points` decimal(12,3)), one row per parsed entry per release. `RankingRepository.SaveAsync` hashes the snapshot (every stored column of every row plus the federation date; a scrape date is excluded) and compares it with the feed's newest release (greatest `Id`): equal means only `LastSeenAt` moves (`Unchanged`); different means a new release with its rows (`Inserted`). Nothing is ever updated except `LastSeenAt`, so all releases are the history and the newest per feed is current. Two views (raw SQL in the initial migration, not mapped in EF) serve the planned consumer app: `CurrentRankings` exposes every row of the newest release per feed, and `CurrentCountryRankings` collapses it to one row per country — the best-placed entry (`MIN(Ordinal)`) plus `RankedEntrants = COUNT(*)` of the country's rows.

The connection string `WorldRankGuesserConnection` in `appsettings.json` points at the Docker Compose SQL Server with a committed dev password; override it elsewhere via the `ConnectionStrings__WorldRankGuesserConnection` environment variable. Repository tests run on SQLite in-memory through `EnsureCreated`, which is why "newest" is by `Id` and never by ordering on `FirstSeenAt` (SQLite cannot order by `DateTimeOffset`); the view is only verified against the real server. Because the view is raw SQL outside the EF model, a later migration that renames or retypes a column it projects must drop and re-create the views themselves, in that same migration, since EF will not notice the mismatch.

## Architecture

**The unit of work is a feed, not a sport.** `serviceconfig.json` holds a flat `Rankings` array of `RankingItem`s (bound to `RankingSourcesOptions`). Each item says what to stamp on the rows (`Sport`, `Event`, `Gender`), where to fetch (`Url`), which parser understands the response (`Source`), and optionally which `UrlResolver` turns the configured URL into the real one, which `Fetcher` requests it ("Http" by default, "Curl" for a feed that only answers curl), which `Selector` names one ranking inside a response that holds several, and, for a list that comes in pages, a `{page}` placeholder in the `Url` plus `FirstPage` when the API counts from 0 (WTA doubles). `Enabled: false` plus a `Note` keeps a dead feed documented without fetching it.

**Pipeline per run** (`Program` → `RankingUpdater` → `RankingSourceRunner` → `IRankingRepository`):

1. `Program.cs` parses the command line into a `FeedFilter` (`Configuration/FeedFilter.cs`: repeatable `--only <pattern>`, anything else is a usage error, exit 1; the host gets no args so its command-line provider never sees the flag), builds the generic host (configuration, logging, DI only; no hosted service), runs `IRankingUpdater.UpdateAllAsync(filter)` once and returns exit code 1 if any feed failed.
2. `RankingUpdater` takes the enabled items, throws `InvalidOperationException` (a config error, like an unknown `Source`) if any `--only` pattern matches none of them, then runs the matching items in parallel, catches per item, saves each snapshot through `IRankingRepository` from its own scope, and returns an `UpdateSummary` (feeds, inserted, unchanged, failed). A pattern matches an item when its words appear, in order, as whole words of `RankingItem.Describe()` ("Sport Event Gender", the name the logs print), case-insensitively: `Cricket` selects five feeds, `Cricket ODI` two, `Cricket Women` two (the event is skipped), `Gymnastics` eighteen and `Cricket ODI Women` one; `Women Cricket` matches nothing because order matters. `--only` never re-enables a disabled item.
3. `RankingSourceRunner` resolves the URL (`IUrlResolver` → `ResolvedUrl(Url, RankingDate?)`), fetches it (the `IHttpFetcher` whose `Name` the item's `Fetcher` gives), parses it (`IRankingParser` → `ParsedRanking(Entries, RankingDate?)`) and builds a `RankingSnapshot` via `RankingSnapshotBuilder`. A URL carrying `{page}` is fetched page by page from `FirstPage` (default 1), each page parsed on its own, until a page yields no entries (dropped): the entries concatenate, the ranking date is the first page's and a later page with another date throws `ParseException` (the list changed between pages), more than 100 pages still yielding entries throws too (the API ignores `page`), a page that cannot be fetched fails the whole feed (a list with a hole would be stored as a shorter release; the previous one is better), and `FirstPage` on a URL without `{page}` is a config error, as is `{page}` with any resolver but `Identity` (the others `string.Format` the URL, where `{page}` is a format error). The builder: every entry kept and ordered by position (ties keep feed order), `TeamName` always taken from `CountryNames` for the code (an unknown code throws `ParseException`), equal duplicate entries rejected with `ParseException` (record equality is the guard), and the ranking date chosen as parser's date, else resolver's date, else today from `TimeProvider` with `IsFederationDate = false`. A failed fetch yields null; a malformed response throws `ParseException`; an unknown `Source`, `UrlResolver` or `Fetcher` name throws `InvalidOperationException` because that is a config error.
4. Parsers, resolvers and fetchers are registered as plain `IRankingParser` / `IUrlResolver` / `IHttpFetcher` singletons in `AddRankingPipeline`; the runner indexes them by `SourceName` / `Name`. `HttpFetcher` is registered last on purpose: the resolvers inject a single `IHttpFetcher`, DI hands a single dependency the last registration, and their preliminary requests must keep going through `HttpClient` (`RankingPipelineRegistrationTests` pins this). Both fetchers are handed out only behind `CachingFetcher` (see Fetchers), the concrete types being registered as themselves for it to wrap. Nothing outside `Persistence/` and `Program.cs` references EF Core.

**Parsers are pure functions of the response.** `Parsing/IRankingParser` returns `ParsedRanking(Entries, RankingDate?)` of `RankEntry(Position, ISO3, Competitor?, Points?)` and knows nothing about sport, event or gender. There is deliberately no country name on the entry: parsers never pass the feed's spelling, and the builder names every row from `Utilities/CountryNames.cs`, a committed ISO3 → name table (seeded from .NET's `RegionInfo`, abbreviations written out, plus `XKX`, `WI`, `ENG`, `SCO`, `WAL`, `NIR`), so a name never depends on the host's ICU data. `Competitor` is the athlete, pair or group when the federation ranks people, `Points` its headline points or rating (ICC: the rating). A parser emits one entry per ranked entity and the builder stores them all; countries are derived in the `CurrentCountryRankings` view (see `docs/superpowers/specs/2026-09-17-store-all-entries-design.md`). Two base classes do the boilerplate: `JsonRankingParser<TRoot>` deserializes into a small DTO record declared by the subclass (unknown properties are ignored, so declare only what you need; use `[JsonPropertyName]` for snake_case or hyphenated keys) and `HtmlRankingParser` selects rows by XPath and maps each `HtmlNode`. One parser per federation feed shape: `Fih`, `WorldRugby`, `Svns`, `EspnTennis`, `Wta`, `VolleyballWorld`, `Icc`, `FifaV3`, `Fiba`, `Bwf`, `Wbsc`, `Fig`, `WikipediaIihf`. Two parsers need the item's `Selector`, because their page holds several rankings: `Fig` ("<series> / <apparatus>", e.g. "World Cup / Vault": one FIG page holds every apparatus table of both the World Cup and the World Challenge Cup series) and `WikipediaIihf` ("Men" or "Women": Wikipedia's "IIHF World Ranking" article holds both tables, each looked for only inside its own h2 section so a missing table is never answered with the other; teams shown as `NR` or `new` have no rank and are skipped, any other non-numeric rank throws). `IRankingParser.Parse(response, selector)` passes it through and every other parser ignores it. FIG rows are athletes (rhythmic group events: national groups, whose name is the country); only the World Cup series is configured, with the apparatus as `Event`. Country codes are normalized inside the parser because only it knows what the feed emits: `IOCToISO3()` for IOC-style codes (its table also holds the federation-only codes: Volleyball World's `AGU`/`CUR`/`FAR`/`MSH`/`MLD`/`PAU`, FIFA's `CTA`/`EQG`/`TAH`, the ICC's and FIH's `ESW`/`SDA`; the ICC's `SRL` is Sierra Leone and `SL` Sri Lanka), `CountryUtil.TryGetISO3FromCountry` for names or slugs (throw `ParseException` naming the value when it does not resolve, so a new country shows up in the logs and in the fixture test rather than silently vanishing). Feeds that publish a ranking date override `GetRankingDate` on the base class and parse it with `IsoDate.Parse` (throws `ParseException` for a non-ISO value): ICC `rank_date`, WTA `rankedAt`, ESPN `update`, WBSC row `date`, FIBA's `rankingDatesselect` dropdown, World Rugby's root-level `effective.label`. FIH and Volleyball World only stamp file-generation time and return null; FIG and the Wikipedia IIHF article show no date at all. FIFA's date comes from the resolver (the `iso` of the chosen schedule entry; the digits in the id are not the ranking date) and WBSC's also from its resolver.

**Fetchers.** `HttpFetcher` ("Http", the default) is `HttpClient` with a browser-like User-Agent, which several federation sites insist on. `CurlFetcher` ("Curl") runs the machine's `curl` for a feed that refuses .NET's TLS handshake but answers curl, and sends a descriptive User-Agent (`SportsRankingService/1.0 (+repo URL)`) instead of imitating a browser. It is cross-platform by never involving a shell: `UseShellExecute = false` plus `ProcessStartInfo.ArgumentList` (no quoting rules, no `NUL` versus `/dev/null`, no PowerShell `curl` alias), the body read from stdout decoded as UTF-8 (without that Windows applies the console code page and "Türkiye" arrives mangled), `--disable` first so a user's `.curlrc` cannot interfere, `--fail` so HTTP 400+ is a non-zero exit, `--max-time 60`, both pipes drained concurrently, and the process killed on cancellation. A missing curl binary or a non-zero exit is a failed fetch (null plus a log line), like any other transport failure. `CurlFetcherTests` run the real curl against a loopback socket, so they need curl on the PATH and prove the behaviour on whichever OS runs them. `CachingFetcher` decorates each of the two (same `Name`, one cache per wrapped fetcher) and requests a URL once per run: it shares the in-flight task, not just the result, because the feeds run in parallel, so the 18 FIG items cost three requests, the two ice hockey items one, and the WBSC and SVNS resolvers read their preliminary pages once instead of once per item. A failed fetch is shared too (eight feeds on a dead page fail from one request). The cache lives as long as the singleton, which is one run in this run-once process; a long-lived host would need a cache per run. Do not answer a block by forging a browser's TLS fingerprint or solving a JavaScript challenge; find another client the site accepts as itself, or another source.

**URL resolvers** handle feeds whose ranking URL depends on a preliminary request; the configured `Url` carries a `{0}` placeholder. `FifaDateId` reads the newest ranking-schedule id from the FIFA page's `__NEXT_DATA__` (`ranking.dates`, newest by ISO timestamp, works for the men's and women's pages alike). `WbscReleaseDate` reads the release-date list embedded in rankings.wbsc.org and takes the newest for the `sportId` in the item's URL, because the WBSC API returns an empty list for any other date. `SvnsSeries` reads the season's series ids from svns.com and picks the one whose World Rugby series metadata `sport` is `mrs` (men) or `wrs` (women). `Identity` is the default.

**Adding a feed.** Capture a real response into the git-ignored `tests/SportsRankingService.Tests/Captures/` to learn its shape, add a synthetic sample of that shape to `Samples/generate.mjs` (regenerate, list it in `SAMPLES.md` and in `Feeds.All`); write the parser test against the sample (red); add a `<Feed>Parser` subclassing one of the two base classes with a unique `SourceName`; register it in `AddRankingPipeline`; add the item(s) to `serviceconfig.json`. If the URL needs a discovered id or date, add an `IUrlResolver` the same way. If one response holds several rankings, give each item a `Selector` and have the parser interpret it. Never commit a capture.

**Country handling decisions.** Only the code identifies a country; `TeamName` is display text derived from it and every feed gets the same spelling (`USA` → "United States of America", `KOR` → "Korea", `TUR` → "Türkiye", `COD` → "Democratic Republic of Congo", `COG` → "Republic of Congo", `PYF` → "French Polynesia" for FIFA's Tahiti). Change a name in `CountryNames.cs` and pin it in `CountryNamesTests`. England, Scotland, Wales and Northern Ireland map to `GBR` when they arrive as names (BWF); FIFA's own `ENG`/`SCO`/`WAL`/`NIR` codes are kept as emitted. West Indies stays `WI` (no ISO3 code). Kosovo is `XKX`. BWF doubles pairs produce one row per partner with the pair's position and points, each row carrying that partner's own name; "Athlete Independent Neutral" players are dropped, while a "<COUNTRY> Independent" label (a player competing outside their federation, seen 2026-09-22) counts for that country. WTA rows whose `countryCode` is null or `NCD` (neither an ISO nor an IOC code; a few players deep in the doubles list) are dropped for the same reason: no country to count for. BWF's full lists need two collapses, both keyed on BWF's player ids inside `BwfParser` (the builder's duplicate guard is untouched): a row echoed inside a tie block (a new row id, the same player ids, rank and points; 172 echoes over the five lists on 2026-09-18) is one entry, and an echo that disagrees on rank or points throws; and a player whose two different pairs tie on rank and points is listed once at that rank, because an entry names the player and not the pair, so the two would be identical (decided 2026-09-18 over putting the partner into `Competitor` or adding a Partner column). BWF spells some countries its own way ("Macau China", "Brunei Darussalam", "National Olympic Commitee KENYA", ...); those are aliases in `CountryUtil` pinned in `CountryUtilTests`.

**Null handling idiom.** `NotNullOrEmpty()` (in `Utilities/NullOrEmptyExtension.cs`) throws `ArgumentNullException` with the caller expression if the value is null or an empty collection; the resolvers use it on page-scraping steps that must not silently succeed.

## Current state

Live on 2026-09-22: 54 feeds enabled, parsing and saved with exit 0 (about 17,300 entry rows per run, 10,900 of them badminton), 1 disabled (ATP doubles). On 2026-09-18 the five BWF badminton feeds went live through `CurlFetcher` (Cloudflare refuses .NET's TLS handshake on TLS 1.2 and 1.3 with any User-Agent, although the request bytes equal curl's; curl passes with a descriptive User-Agent) and ice hockey went live for men and women from Wikipedia's "IIHF World Ranking" article through the MediaWiki REST API, because iihf.com answers every scripted client with a Cloudflare challenge; the two ice hockey items also use the Curl fetcher, since Wikimedia's User-Agent policy asks scripts to identify themselves and only that fetcher does. Since 2026-09-22 BWF answers 500 for any page that includes row 1558 of men's singles (2,201 players) or row 1604 of men's doubles (1,715 rows), one broken record in each on their side (the neighbouring rows are fine; probed one row at a time with `pageKey=1`), so those two lists are capped at `pageKey=1500` with a dated note until `pageKey=2000` answers 200 again; paging them would not help, since no page size avoids the row. Gymnastics (18 FIG feeds: every apparatus of the World Cup series for men's and women's artistic and rhythmic) was dropped in the 2026-09-15 refactor and restored on 2026-09-16; the 18 items read the same three pages, which since 2026-09-18 are requested once each per run through `CachingFetcher` (a run of the 26 gymnastics, WBSC, sevens and ice hockey feeds went from 35 requests to 14). On 2026-09-17 the feed's own country spelling stopped being stored: `TeamName` now always comes from the committed `CountryNames` table, eleven federation-only codes were added to the IOC table, the ICC's `SRL` (Sierra Leone) was untangled from Sri Lanka, and the soccer feeds' `Sport` became "Soccer"; the database was dropped and repopulated rather than migrated. Persistence was redesigned on 2026-09-15 (spec: `docs/superpowers/specs/2026-09-15-persistence-redesign-design.md`): releases with insert-on-change, federation ranking dates where feeds publish them, Docker Compose SQL Server, code-first migrations, run-once console.
